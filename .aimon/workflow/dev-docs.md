# Dev Docs 工作流
<!-- dev-docs-workflow:v6 -->

> 本段由 VibeSpace UI 装配（在「Dev Docs」侧栏可卸载/重装更新）。
> 内容与 VibeSpace 仓库 CLAUDE.md 同步，剔除了 VibeSpace 仓库专属内容；具体函数路径以 VibeSpace 仓库为参考举例，目标项目可改用各自等价物。

本项目启用了 **Dev Docs 三段式工作流**。当用户提出一个**新功能、重构、bug 修复或任何非平凡的改动**时，你 **不要立刻改代码**，按以下流程推进。

流程整体**偏审慎多于速度**：宁可多确认一轮，也不在错误假设上跑远。琐碎到连任务都不构成的请求（格式化、改一个 typo、答疑），可以绕过本流程直接做，用自己的判断。

**大哥是非程序员，只关心大方向和验收结果**。技术选型、命名、文件结构、库选择、实现路径——这些 AI 自己定，不要拿来让用户挑。能拿来给用户确认的只有两类:(1) **大方向**——这次任务到底要解决什么、什么样算解决了；(2) **有用户感知差异的分叉**——A 路径和 B 路径会导致用户最终**看得见**的不同（界面不同 / 数据会不会动到 / 能否撤销 / 操作步骤变没变）。**纯内部实现**的分叉（用 A 函数还是 B 函数、放 utils 还是单独文件、要不要抽 helper），AI 自决，不要打扰。

**确认只发生在一处：plan 呈现后**（方向、目标、验收方式是否对）。Context 阶段写完**不停下等用户**——AI 自己审完直接进 Tasks 阶段。把确认预算压到一次。

## 0. 会话启动与按需 Skill

如果环境变量 `AIMON_SESSION_PROMPT_PATH` 指向一个存在且可读的文件，开始执行任务前必须先读它（这是 VibeSpace UI 在 session 启动时按当前 task 名命中的 `.aimon/skills/` 内容快照）。

读完后只把它当作本任务的执行约束和套路提示，不要把整段内容复述给大哥。文件不存在、路径为空或不可读时，记录一句"按需 skill prompt 未注入/不可读"，继续按本工作流执行，不要反复重试。如果项目独立运行（不通过 VibeSpace UI 起 session），该环境变量不存在属正常情况。

### 跟大哥说话的规矩（硬性，贯穿全流程）

大哥明确说过他不懂代码。所有面向他的输出（plan 摘要、handoff、对话回复、错误说明）必须遵守：

- **专业术语括号解释**：第一次出现时用一句白话翻译。例："worktree（git 的临时副本，几个并行任务互不踩脚）""daemon（在后台一直跑的小程序）""mutation（会改数据库或文件的操作）""payload（一次请求里夹带的数据）"。
- **翻译成"用户看得见的变化"**：别说"加了 zod 校验"，说"前端发非法数据时后端会拦下来并提示"；别说"重构了 sessions 路由"，说"会话列表打开速度变快了，行为不变"。
- **让用户拍板的事永远是"要不要这样做 / 在哪里能验收"**，不能是"用 A 还是 B"。后者是 AI 自己的活。

## 1. Plan 阶段 — 先规划

1. 从用户描述里提炼一个简短的 **任务名**（**必须使用中文**；禁止含 `/ \\ : * ? " < > |`）。**AI 自己定即可，不要就任务名本身找用户确认**——只要中文、不含禁用字符、能一眼看懂本次做什么就行；万一起偏了，用户会在 plan 呈现时一并纠正。
2. 创建目录 `dev/active/<任务名>/`：
   - 若不存在，直接创建。
   - 若已存在且**内容与当前需求无关**（残留的旧任务同名了），先把旧目录整体 `mv` 到 `dev/archive/<任务名>-<YYYYMMDD-HHMM>/`（没有 `dev/archive/` 就顺手建），再创建新目录。**不要覆盖写入或就地修改旧文件**，以免吞掉用户前一次的上下文。
   - 若已存在且**就是本次要继续的任务**（用户说"继续 <任务名>"等），直接读取继续，不要归档。
3. 写入 `dev/active/<任务名>/<任务名>-plan.md`，内容包含以下段落：
   - **大哥摘要（必写，最前面，3–5 行白话）**：用大白话告诉大哥三件事 —— 这次要做什么、做完后他能在**哪里点哪里**看到、需不需要担心动到他现有的什么数据/界面。专业术语必须括号解释。这段是给非程序员看的，不要写"我们将引入 X 模块"。**大哥主要靠这段决定要不要点头**，所以写得不像人话就是不合格。
   - **风险醒目块（命中才写，紧跟大哥摘要正下方）**：本任务若命中"会动大哥现有数据 / 不可撤销 / 含破坏性变更"任一，必须用 GitHub 警示块（`> [!WARNING]` 这种带颜色图标的提示框）单独拎一条出来，一句白话说清风险点，让大哥一眼看到、别划过去。无此类风险则整段省略，不要为凑格式硬写。
   - **目标**：解决什么问题，以及**可验证的验收标准** —— 用能跑的测试、能执行的命令、能观察的指标/截图来表达，不要写"让它能用"这种弱目标。举例：
     - "加校验" → "对非法输入写一个失败的测试，然后让它通过"
     - "修 bug" → "写一个复现 bug 的测试，然后让它通过"
     - "重构 X" → "确保重构前后测试全部通过"
   - **非目标 (Non-Goals)**：一到三行，明确列出**本次任务不做**的事 —— 容易被顺带扯进来的相邻模块、看起来相关但不在本轮的功能。写出来是为了给自己划好发散边界，执行阶段越界时可以回头对照。
   - **实施步骤**：有序列表，粗粒度即可。每一步尽量带一个"如何验证"的小尾巴。
   - **边界情况**：本方案在什么极端输入、异常状态、边界条件下会失效？列出已知的、需要在实现/测试时覆盖的。
   - **风险与注意**：已知的坑、需要确认的**假设**、可能波及到"关键文件"之外的模块。
4. **停下，用确认选择框呈递 plan，等用户拍板**（不是发一段文字干等回复——必须给一个能点的选择框）。固定给三个选项，**编号顺序固定**：
   1. **开始做** —— 确认方案，进 context/tasks 开干；
   2. **让 codex 先评估一遍** —— 派一次 `codex:rescue` 评审本 plan，把意见并入、在 plan.md 末尾补 `## 多模型 Plan 会审` 段后**重新呈递一次**。**此项仅当本 plan 末尾还没有 `## 多模型 Plan 会审` 段（即还没经 codex 看过）时才出现**，已评过就不再给这一项；
   3. **再改改 / 先这样** —— 方向或范围要调整，按用户意见改完 plan 再呈。
   呈递时**附一行把握度**：`把握度：高 / 中 / 低 —— <一句为什么>`（AI 对这个方案能一次做对的自评；中 / 低时大哥就知道要多看两眼、多问一句）。**若本项目接了即时通知通道**（飞书 / 钉钉 / Slack 等），呈递时**把 plan 摘要 + 上面三个选项一并推过去**，方便用户不在电脑前也能远程拍板（具体推送做法见各项目自身约定）。**这是整条流程里唯一一次需要用户点头的地方**——之后 context、tasks、执行都不停下等。

### 写 plan 时的硬性规则（贯穿第 3 步）

- **假设要显式（写在 plan 里给自己存档，不专门追问用户）**：心里默认的前提、依赖的接口行为、数据量级、边界场景，都写进 plan。**只有当假设错了会改变验收方式或大方向时，才回头跟用户确认**；纯技术假设自己定。
- **大方向有分叉才问**：用户这句话能理解成 A 或 B，且 A、B 会让**用户最终看到的东西不一样**（界面不同 / 数据流向不同 / 能否撤销不同 / 操作步骤变没变），列出来让用户挑。**差别只在内部实现路径的，AI 自决**，不要列给用户看。
- **显著更简的路才说**：发现一条**显著**简单的路（少一半工作量、少动一个模块、少一个外部依赖），先说出来让用户决定。**微小优化、个人审美的"我觉得这样写更好"，自决，不要回头问**。
- **影响验收方式才停**：读代码后发现"这个验收标准实际验证不了 / 用户描述与代码现状不符"才停下来问。**纯实现细节看不懂的，AI 自己研究，不打扰**。
- **UI 改动必须有浏览器可观察的验收项**：如果本任务涉及前端代码（页面、组件、样式、交互），plan 的**验收标准里必须至少有一条"在浏览器里能看到/能点出来"的行为描述**，大哥能照着这条去验收。缺这一条视为 plan 不完整。

### Plan 阶段的双模型会审（按需触发，不再默认开）

完整档 plan 由 **Claude 单独主笔**即可，不再每次都拉 Codex。只有命中下面任一情形，才追加**一次** Codex 会审（用 `codex:rescue` 插件）拿第二意见：

- 改动会动数据 / 改表结构 / 含破坏性变更；
- 跨多模块，且 AI 对方案的自评把握度为"中 / 低"；
- 大哥明说"要会审 / 多看一遍 / 叫上 codex"。

**为什么改按需**：业界共识是跨模型互审属"大改才动用的重武器"（慢、贵），默认每次跑性价比低、还拖慢交付。把审慎留给真正高风险的改动，小改和有把握的改动 Claude 直接出方案。

命中会审时的做法（3 步，AI 自动跑完，大哥只看最后 plan）：

1. **Claude 出 plan 草案 + 事实包**：扫 `dev/memory/auto.md` + `manual.md`、读必要代码，整理出验收标准 / 非目标 / 现状 / 已知风险 / 大哥偏好——给没有项目记忆的 Codex 补上下文。
2. **派一次 `codex:rescue` 评审**（仅一次，不再让它综合主笔）→ 闭合问题："基于 Claude 草案，结构上有没有显著更简的写法？落地风险点？有没有上游依赖 / 边界情况 / 数据影响漏了？列 ≤30 行补充清单。"
3. **Claude 综合定稿**：吸收 Codex 清单，自己定稿 plan、白话化大哥摘要后呈递。

**Codex 会审并行后台跑、不同步干等**（项目记忆 `feedback_codex_review_timeout`）：先按 Claude 方案推进/呈递，Codex 返回后再合并修改。外部工具失败 / 超时：重试一次仍败就**回退 Claude 单写**，在 plan.md 末尾记一行 `会审跳过：<原因>`，绝不因外部基础设施阻塞 plan 交付。

命中会审的 plan.md 末尾带一段 `## 多模型 Plan 会审` 记录痕迹（`> [Codex 评审] …` / `> [Claude 定稿] …`）；没命中会审的 plan **无需**此段。

### 远程拍板：停下等大哥拍板时主动上报通知通道（接了即时通知通道才生效）

如果本项目接了**即时通知通道**（飞书 / 钉钉 / Slack 等，让大哥不在电脑前也能远程拍板），那么你**每次停下来等大哥拍一个选择题 / 做 y/n 确认 / 确认 plan 定稿**时，先把【问题 + 选项】主动上报给通知通道，再弹你正常的选择框——通道后端据此把带编号的选项干净地推到大哥手机，他点一下就回传答案。**后端不该去读你的终端屏幕**（扫屏会把"转圈思考"乱码残影推过去），上报必须由你主动发起。**本项目没接通知通道就整节忽略。**

（VibeSpace 项目：这套上报由全局 skill `ask-dage`（"问大哥"）承载——命中它、按它指引跑 `ask-dage.mjs` 脚本把问题+选项上报即可，后端**不再扫终端、不再解析屏上暗号**；其他通道按各自约定接后端。）

规则：① 选项编号（第 1 个=1、第 2 个=2……）就是大哥点按钮回传给你的按键，**编号顺序必须和你随后选择框里的选项一一对应**；② y/n 确认写成两个选项「是 / 否」；③ 进度别报（后端自己读 dev-docs 步数）；④ 这是**额外动作**，不替代你正常的选择框——两个都要；⑤ 只在"真要大哥拍板"时上报，普通进度汇报别报。

**plan 定稿确认特例**：当这次拍板是 plan 写完、停下等大哥点头那一次，上报时带「附 plan」标记——接了通道的后端会把整份 plan 摘要 + 附件一并推给大哥再附选项按钮（VibeSpace 行为，其他通道酌情）。三个选项固定：`开始做` / `让 codex 先评估这个 plan` / `再改改 / 先这样`（`让 codex 先评估` 仅当本 plan 末尾还没有 `## 多模型 Plan 会审` 段时才列，已评过就去掉、其余顺延）。

## 2. Context 阶段 — 上下文盘点（AI 自用，**不停下等确认**）

用户确认 plan 后，写入 `dev/active/<任务名>/<任务名>-context.md`。**这一段是给 AI 自己看的，大哥不审**——他不懂代码、看了也没价值，所以写完直接进 Tasks 阶段，**不要发"context 写好了请确认"这种消息**。

但仍然要认真写，因为：(1) 执行阶段会回头对照边界；(2) 归档评审会读它产出 auto.md 记忆；(3) 上下文耗尽换会话时新一轮会话靠它衔接。

内容包含：

- **关键文件**：会读/会改的文件清单，附上相关符号或行号范围。这张清单就是本次改动的**边界**——执行阶段原则上只动这里列的文件；真要溢出，先回来补 context。
- **决策记录**：为什么选 A 不选 B，权衡是什么。每个决策必须回答一句：**"资深工程师看到这个方案，会不会觉得过度设计？"** 如果会，就简化到不会为止。具体忌讳：
  - 不做用户没要的功能
  - 不做只用一次的抽象
  - 不做没人要求的"灵活性"或"可配置性"
  - 不为不可能发生的场景写错误处理
  - 200 行能解决的问题不写 500 行
- **依赖与约束**：上游 API、数据结构、兼容性要求。

写完直接进入 Tasks 阶段。

**唯一例外**：写 context 时发现 plan 实际不可行（关键文件不存在、依赖接口不是想象的样子、验收方式实际无法验证），回去改 plan 并**重新征求用户确认一次**。这是整条流程里 plan 之外唯一的回头确认情形。

## 3. Tasks 阶段 — 清单 + 执行

用户确认 context 后，写入 `dev/active/<任务名>/<任务名>-tasks.md`：

```markdown
# <任务名> · 任务清单

- [ ] 步骤 1 → verify: <怎么验证这步完成了>
- [ ] 步骤 2 → verify: ...
- [ ] 步骤 3 → verify: ...
```

每条任务都带 `verify:`，这样你可以自己跑、自己判断是否通过，不必每一步都来问用户。

**可选**——完整档 / 跨多文件任务若想要 UI 侧栏精确显示读写白名单，再额外写一份机器可读副本 `<任务名>-tasks.json`（给 IDE 插件 / 侧栏 UI / 外部脚本消费，免得它们正则解析 markdown 复选框）；否则只写 tasks.md 一份足够，不必写 json：

```json
{
  "task": "<任务名>",
  "steps": [
    {
      "id": 1,
      "title": "步骤 1",
      "verify": "...",
      "status": "todo",
      "read_files": ["path/to/some/file.ts", "path/to/another.tsx"],
      "write_files": ["path/to/some/file.ts"]
    },
    {
      "id": 2,
      "title": "步骤 2",
      "verify": "...",
      "status": "todo",
      "read_files": ["..."],
      "write_files": ["..."]
    }
  ]
}
```

- `status` 取值：`todo | doing | done | blocked`。
- `read_files` / `write_files`：**选填**——只在写了 tasks.json、想要侧栏白名单守护时才填；不写 json 时省略。允许 glob（如 `src/routes/*.ts`），AI 自查时心算判断越界。详见下方 `### 执行时的硬性规则` 中的"读写白名单"段。
- **tasks.md 是状态的唯一真源；执行期不要逐步回填 tasks.json 的 `status`**。每完成一步只改 tasks.md 的 `- [ ]` → `- [x]`，看板进度由解析 tasks.md 的复选框得出，不需要同步 json。tasks.json 在建任务时写一次（步骤结构 + `read_files`/`write_files` 白名单），执行期不用再动它的 `status` 字段——这样消除了"两份文件状态对不上"的老毛病。
- **唯一例外是 `blocked`**：某步卡住时，把原因写进 tasks.md 对应行尾，并把 tasks.json 该步 `status` 改成 `blocked`（这是 md 复选框表达不了、看板要专门染色的唯一状态）。其余 `todo/doing/done` 一律以 md 复选框为准。

然后 **开始执行**。执行节奏规则：

- 每完成一个步骤，**立即** 把对应行从 `- [ ]` 改成 `- [x]`，再做下一步；不要批量勾。
- 过程中若发现 plan 或 context 有遗漏，**先更新对应 md 文件**，再继续。
- 若途中发现 tasks 需要拆分或新增，随时修改 `tasks.md`。

### 执行时的硬性规则（外科式改动）

- **只碰必须碰的**：每一行改动都要能追溯回 plan/tasks 的某一条。看不顺眼的相邻代码、注释、格式，**一律不要动**。
- **不要顺手重构**：没坏的东西别"改进"，哪怕你觉得自己会写得更好。保持现有代码风格，即使你不认同。
- **看到无关的死代码就提一嘴，不要删**：在回复里告知用户"顺便看到 X 似乎没在用"，由用户决定是否另起任务清理。
- **自己引入的孤儿要清掉**：本次改动让某个 import/变量/函数不再被使用，就该在本次删掉。预先存在的死代码不在此列。
- **不要加投机性代码**：别写"以后可能用到"的抽象、配置点、错误处理。当下不需要就不写。
- **熔断：同一步骤连续失败 2–3 次就停**：如果 `verify` 没通过、报错没解决，**修改 2 次仍然不过就停手**。不要越改越大、不要为了凑绿灯去动任务范围之外的底层代码或测试用例。停下来，把错误日志、你试过的方案和当前的疑惑打印给用户，等人介入再继续。
- **静态类型语言必须过类型检查**：如果项目使用 TypeScript / Rust / Go / Kotlin / Swift 等带静态类型的语言，且当前步骤改动了源码，`verify` 至少包含一次**项目层面的类型检查命令**并且结果为成功（具体命令参见项目 README、`package.json` scripts、`Makefile`、`justfile` 或构建配置）。不允许用"人工看过"替代；"单测通过"也不等于类型检查通过。
- **读写白名单**（选填守护）：若写了 tasks.json 并声明了每步 `read_files`（允许读）/ `write_files`（允许改），verify 通过后、勾完成前就跑 `git diff --name-only HEAD` 与本步骤 `write_files` 比对——越界文件不算完成，要么回滚越界改动、要么停下来回 plan 扩范围；没写 json 时，AI 仍要心算判断有没有动到本任务之外的文件。glob 写法允许（如 `src/routes/*.ts`）。**目的**：堵住"AI 顺手改无关代码"的老问题。
- **破坏性变更协议**：本步若涉及以下任一事项，**必须先 grep 引用图、列受影响清单给大哥、等大哥点头才动手**：
  1. 删除任意源码文件
  2. 删除任一文件中 ≥5 行连续业务代码（注释、空行、配置文件不计）
  3. 修改、重命名或删除任一被跨文件 import 的导出符号（`type` / `interface` / `function` / `class` / `const` / `default export`）
  4. 修改、删除或重命名任一 HTTP 路由 / WebSocket 消息类型 / IPC 通道
  5. 修改 SQLite 表结构（列增删改、索引、约束变化）

  触发后该步 `verify` 必须额外包含一次"修改后 grep 同符号 / 同路径，确认无残留旧引用"。**目的**：防止"删了 API 但前端还在调"这类事故。

## 操作日志规则（硬性）

**所有"用户可感知的功能改动"在交付前必须配套操作日志**——前端埋点（项目 UI 日志面板）、后端日志能落盘到固定路径（VibeSpace 项目落在 `packages/server/data/logs/YYYY-MM-DD.log`，其他项目按各自约定）。目的是让你自己和用户能在"浏览器 + 一个文件"里回放整次操作，后续测试/排障不用反复复现。

### 适用范围（什么算"用户可感知的功能"）

**必须埋**：
- 新增 UI 操作（按钮、菜单项、对话框提交、拖放、快捷键等用户主动触发的行为）
- 新增 mutation API（写数据库、改文件、起/停进程、调外部 CLI、发网络请求等会改变系统状态的后端路由）
- 修复影响用户行为的 bug（用户能感知到行为变了，就要埋；否则它不是 bug 而是重构）

**豁免**（不要强行加日志，否则规则会变废纸）：
- typo / 文档改动 / 注释修改
- 纯重构、纯样式调整、纯类型修复（行为没变）
- 内部工具函数、helper、纯函数、格式化器
- 轮询 / 心跳 / 健康检查 / WS 订阅确认（会日志风暴）
- 测试代码、mock、fixture
- 进程启动脚本里的路径打印之类的运维友好输出（保留 `console.log` 即可）

### 起止配对（默认形态）

一次"操作"至少产生两条日志：
- **开始**：`level=info`，`msg='<action> 开始'`
- **终点**：成功 `level=info msg='<action> 成功 (Nms)'`；失败 `level=error msg='<action> 失败: <reason>'` + `meta.error = { name, message, stack }`

**不要只记一条**：只有开始没有终点，排障时无法判断操作是"卡住"还是"完成"；只有终点没有开始，无法知道耗时。

### 工具

- 前端 **必须用** 项目自带的 logAction 包装器包装 mutation（VibeSpace 项目用 `logAction(scope, action, fn, ctx?)`，见 `packages/web/src/logs.ts`）；其他项目用各自等价物。手动两次 `pushLog` 只在"这次日志跟任何异步调用无关"时用（极少见）。
- 后端 **必须用** 项目自带的 serverLog 包装器（VibeSpace 项目用 `serverLog(level, scope, msg, extra?)`，见 `packages/server/src/log-bus.ts`）；其他项目用各自等价物。不要直接 `console.log` 进业务路径——它不会到 UI 日志面板也不会落盘。
- `scope` 用小写单词（`project` / `session` / `docs` / `git` / `installer` / `server` / ...）；`action` 用动词（`create` / `start` / `archive` / `delete`）。

### 必填字段 & meta 约束

- 必填：`level` / `scope` / `msg`
- 能拿到就附：`projectId`、`sessionId`、`meta`
- `meta` 必须 **JSON-serializable**（`JSON.stringify` 不抛）且 **≤ 2KB**。不要把整份 diff、整棵 AST、DOM 节点塞进去——失败时写关键标识符 + 简短错误，要详细数据时写到专门的调试通道，不要塞进日志。

### 验收方式（`tasks.md` 的 verify 必须包含）

任何"新增 UI 操作"或"新增 mutation API"任务，其 `tasks.md` 对应步骤的 `verify` 必须显式写出：
- "在 UI 日志面板看到 `scope=X action=Y` 的起止配对"
- 失败分支至少有一次 ERROR 条目被人工触发验证过（如故意断网 / 传非法参数）

没有这条 verify 的步骤不视为完成。

### 日志落盘约定（VibeSpace 项目示例）

- 路径：`packages/server/data/logs/YYYY-MM-DD.log`（UTC 切日，JSONL 每行一个 LogEntry）
- 文件由 `log-bus.ts::appendJsonl` 统一写入；前端日志通过 WS `log-from-client` 回传后端落盘
- 不做自动清理 / 大小滚动
- UI 日志面板只显示内存近 N 条（VibeSpace 是 500 条），不读历史磁盘日志；看历史去 `tail -f` 文件

其他项目按各自约定（路径、滚动策略、内存上限），方法论保持一致。

## Issues 档案

当你在推进**当前任务**时，顺手发现跟本任务**无关**的可疑问题（死代码、看起来没引用的函数/变量、明显错字、可疑的逻辑、老旧注释、未被删干净的遗留等），**不要改代码**，而是**追加一条**到项目根下的 `dev/issues.md`。这份文件是全局问题池，不跟某个任务绑定。

### 追加格式（必须单行）

```markdown
- [ ] <简要描述>（文件 <相对路径>[:行号]；上下文：<一句话>）
```

- 每条必须**单行**——解析器按行切，多行续写会丢数据。长描述就压缩到括号里，或分号分隔。
- 新追加的条目统一用 `- [ ]`（未处理）；处理完才改成 `- [x]`。
- `dev/issues.md` 不存在就创建；存在就 append 一行。**不要**覆盖已有内容。

### 派来处理 issues 的 AI 终端

用户在 UI 的「Dev Docs」→「问题」tab 点"派 AI"按钮时，会把问题文本塞给一个新的 AI 终端，指令里会要求你：

1. 读 `dev/issues.md` 找到对应条目，分析并修复。
2. **处理完一条**，就把 `dev/issues.md` 里**该行**的 `- [ ]` 改成 `- [x]`（不要删行，保留作历史）。
3. 修复涉及多文件时，在本轮回复里简述改动点，仍按外科式原则——只碰必须碰的。

### 和本工作流的边界

- 处理 issues 属于**小任务**，一般不需要走完整的 plan→context→tasks 三段式；直接改代码 + 勾选即可。如果某条 issue 实际上是一个大坑（牵连多模块），停下来跟用户对齐是否升级成常规任务。
- 不要在 `dev/issues.md` 之外另起其它"待办池"文件（如 TODO.md / BACKLOG.md），保持单一入口。

## 规则与边界

- `tasks.md` 由你 (AI) 独占维护，人类只读，不要等用户手动勾选。
- `plan.md` 和 `context.md` 两边都可改；用户若手动编辑了，以他们的版本为准。
- 任务完成（所有 `- [ ]` → `- [x]`）后 **不要自动归档**，等用户在 UI 的「Dev Docs」侧栏里点归档。
- **全部完成后要输出 handoff 摘要（写给大哥看，不是工程笔记）**：最后一条任务打勾的那一轮回复末尾，给一段 ≤ 10 行的完成摘要。**第一行必须是验收指引**——白话告诉大哥"现在去哪里点哪里能看到效果"。后面再列改动涉及的主要文件、跑了什么命令、遗留 TODO（如有）。术语括号解释。没有这段摘要不算交付完成。**末尾必须附一行 `git diff --name-only HEAD` 真实输出**（或 `(已提交，diff 为空)` 短结论），证明本次改动都在本任务的 `write_files` 白名单内；简单档 / 极小档可省 diff 行。
- **分档与留痕**（详见下文「开始一个新任务的首个动作」）：极小档不写文件、简单档只写一份精简 `plan.md`、完整档才写 plan/context/tasks 三件套并在 plan 后停一次等确认。

## 跨任务知识沉淀

任务执行中你可能发现对**未来其他任务也有用**的结论 —— 某个库的坑、项目里非显式的约定、一类操作的通用套路。这些不要只留在本任务的 `context.md` 里，否则任务归档后就找不到了。追写到以下位置之一：

- **项目根的 `CLAUDE.md`** —— 长期生效的项目规则或约定（所有后续任务都要遵守的那种）。
- **项目根的 `dev/learnings.md`**（没有就新建）—— 经验性 tips，还不到规则级别，但下次遇到类似场景能少踩坑。

判断是否该写的唯一标准：**换一个任务还会不会再踩这个坑 / 再用到这个结论？** 会，就写；不会，就不写。只跟当前任务相关的（特定文件的 bug、临时 workaround、当次决策的依据）留在 `context.md` 即可，别往 `CLAUDE.md` / `learnings.md` 里倒 —— 一旦变成噪声，就没人读了。

## 可持续记忆（自动沉淀 + 手动追记）

本项目开启了"可持续记忆"：`dev/memory/auto.md`（自动评审产出）、`dev/memory/manual.md`（大哥手动写）、`dev/memory/rejected.md`（撤回历史）。它是上面"跨任务知识沉淀"的 **补强**，不是替换 —— 原规则里"自觉写 CLAUDE.md / dev/learnings.md"照旧。

- **Plan 阶段的第一步**：在读代码之前先扫三份"项目常量"——`dev/memory/auto.md` / `dev/memory/manual.md` / `dev/ARCHITECTURE.md`（项目架构地图，长期稳定，可选）。前两份找跟本任务相关的经验条目，在 `plan.md` 里 **显式引用**（抄一句或带编号指向），证明你看过；`ARCHITECTURE.md` 找跟本任务相关的章节（如 `@dev/ARCHITECTURE.md#packages拓扑`），让 plan 不用从零摸代码。无相关条目/章节则一句"memory 扫过无相关条目 / ARCHITECTURE 扫过无相关章节"即可。不要装作没这些文件。
- **归档会自动触发评审**：每次点归档按钮，后端 fire-and-forget 拉起评审 CLI 读刚归档的 plan/context/tasks，把"换个任务还会用到"的经验按单行格式 append 到 `auto.md`。UI「记忆」tab 3 秒轮询，新条目会在 2 分钟内出现；评审失败则在 `rejected.md` 留一条 `review-failed:<任务名>`。归档本身永远不被评审阻塞。
- **SessionStart hook 自动注入**：新开 AI 会话时 hook 会把 `auto.md` 最近 30 条 + `manual.md` 全部内容（合计 ≤10KB 截断）塞进系统上下文。也就是说你在本会话早期就 **已经看到** 这些记忆——读不到等于 hook 故障，自行排查。
- **UI 撤回是唯一的修复手段**：auto.md 里写歪了 → 在「记忆」tab 勾选条目 → 点"撤回选中" → 后端把它移到 `rejected.md`（保留历史，不删除）。不要直接手动编辑 auto.md；它是机器产出的文件。
- **长期经验手动追加到 `manual.md`**：任何你觉得"换任务也会用"的偏好、约定、套路，都往 `manual.md` 追加。格式建议与 auto.md 一致（`- [日期 / 来源] 结论（上下文：…）`），但自然段也行——前端会以 raw 原文展示。manual.md 不会被自动评审改动。

## 上下文耗尽的衔接

如果你感觉上下文窗口快满：

1. 把当前进度和下一步明确写入 `tasks.md`（未完成的项 `- [ ]` 加备注说明卡在哪）和 `context.md`（新决策、新发现的文件）。
2. 告诉用户"上下文接近上限，请开新会话只说『继续 <任务名>』，我会读完三个 md 无缝接上。"
3. 新会话里，用户只需说 `继续 <任务名>`，你就先读 `dev/active/<任务名>/` 下三个 md，再继续。

## 开始一个新任务的首个动作

收到需求后，第一步 **不是读代码**，而是：

1. **判断任务量级**（AI 自己定，不要问用户）：
   - **极小**（纯文案 / typo / 改颜色 / 加一个菜单项 / 单文件纯样式微调，一句话能说清的）→ 直接动手，**不写任何文件**，做完一句话告诉用户。
   - **简单档（覆盖绝大多数日常活）**：bug 修复、调整、重构、小的新增（加按钮 / 不动数据的小路由 / 改一个组件内部行为）、或用户明说"小改动 / 按你想法做 / 就一行"——**只要不动数据或表结构、非破坏性、改错好回滚**，就归这档。→ **直接做、全程不停、不调外部模型**，只写**一份精简 `plan.md`**（任务名 + 这次干了啥 + 怎么验收）留痕，做完交付 handoff；**不写 context/tasks**。
   - **完整档（真正值得规划的大改才触发）**：命中任一才走 —— ① 会动数据 / 改表结构；② 破坏性变更（删源码文件 / 删大段业务代码 / 改跨文件导出符号 / 改路由）；③ 跨多模块的较大新功能；④ AI 自评把握度低、拿不准风险。→ 写完整 plan/context/tasks 三件套，**plan 后停一次等确认**；高风险时 plan 阶段按需加一道 Codex 会审（见上文「按需触发的双模型会审」）。
   - **拿不准是"简单"还是"完整"，先往简单档放** —— 跑偏了用户会在交付时纠正，没必要给小改都套全流程。
2. 告诉用户**任务名 + 接下来怎么走**（"任务名叫 X，我直接动手 / 我去写 plan 你看"），不要问"叫什么名字好"。
3. 然后去读代码；完整档写三件套，简单档只写一份精简 plan.md。

---

**本工作流生效的信号**：

- diff 里没有跟本任务无关的改动
- 不再因为"过度实现"反复重写
- 澄清问题发生在动手之前，而不是事后返工
- PR 干净、聚焦，没有顺手重构或"顺便改进"
- **大哥在整个任务里只点过一次头**（plan 阶段），之后只在交付时验收，没有被技术细节、命名选择、文件结构这种琐碎打扰
- 对大哥输出的每段话都看得懂（术语都翻译过，没有"zod / mutation / payload / route handler"裸奔）
