# 검증 규칙 DSL

ID 열에 중복 ID를 넣어도 알 수 없고, 열거 열에 존재하지 않는 값을 넣어도 알 수 없으며, 테이블 간 참조에 이미 삭제된 ID를 넣은 것은 더더욱 알 수 없습니다 — 내보낸 뒤 프로그램이 오류를 내거나 게임 실행 중 죽고 나서야 발견합니다. 검증 규칙 DSL이 바로 이것을 해결합니다: 헤더의 검증 규칙 행에 작은 선언(예: `required`, `unique`, `ref(item@id)`)을 쓰면 열 전체가 실시간 검사 대상이 되어, 잘못 채우면 즉시 빨갛게 표시되고, 내보낼 때까지 기다릴 필요가 없습니다.

> [!tip]
> DSL(Domain-Specific Language, 도메인 특화 언어)은 여기서 "작은 검증 선언 문자열"입니다 — 헤더에 쓰고, 간결하며, 버전 관리 가능하고, 복사·붙여넣기가 됩니다. 그래픽 인터페이스로 규칙을 조립하는 것이 아니라, 글자 그대로 그 몇 글자입니다.

## 8가지 내장 규칙

| 규칙 | 문법 예시 | 작용 |
|------|-----------|------|
| `required` | `required` | 필수, 빈 셀 빨갛게 표시 |
| `unique` | `unique` | 열 전체 고유, 중복 ID 방지 필수 |
| `range(min, max)` | `range(1, 100)` | 수치가 구간 내여야 함 |
| `enum(a, b, c)` | `enum(DAILY, WEEKLY, MONTHLY)` | 이 값들만 허용(고정 열거형) |
| `enum_ref(테이블명@열명)` | `enum_ref(item@id)` | 유효 값이 다른 테이블의 어떤 열에서 동적으로 옴 |
| `len(min, max)` | `len(1, 50)` | 문자열 길이 제한 |
| `regex(pattern)` | `regex(^[A-Z]+$)` | 정규식 매칭 |
| `ref(테이블명@열명)` | `ref(item@id)` | 테이블 간 참조 무결성 — 값이 상대 테이블에 존재해야 함 |

## 조합 규칙: `&&`

여러 규칙을 `&&`로 이어 왼쪽에서 오른쪽으로 순서대로 검사하며, 모두 통과해야 유효합니다:

```
required && range(0, 100)
```

의미: 먼저 필수(비면 바로 빨강), 그다음 0-100 확인(초과하면 빨강).

```
required && unique && len(3, 20) && regex(^[a-z_]+$)
```

의미: 필수 + 전체 테이블 고유 + 길이 3-20 + 소문자와 밑줄만, 네 가지 모두 통과해야 유효.

## 가장 많이 쓰는 네 가지 예시

### 기본 키 ID 열

```
required && unique && range(1000, 99999)
```

필수, 중복 없음, 지정 구간 내 — 이 한 줄을 복사하면 바로 쓸 수 있습니다.

### 열거형 열(값 고정)

```
required && enum(DAILY, WEEKLY, MAIN, SIDE)
```

이 네 값만 넣을 수 있고, 다른 것을 쓰면 빨갛게 표시됩니다.

### 외래 키 열(다른 테이블 참조)

```
required && ref(item@id)
```

넣은 ID가 `item` 테이블의 `id` 열에 존재해야 하며, 외래 키 무결성이 자동으로 보장됩니다.

### 동적 열거형 열(유효 값이 다른 테이블에서 옴)

```
enum_ref(condition_type@id)
```

`condition_type` 테이블에 새 행을 추가하면 이 열의 유효 값 집합이 자동으로 따라 바뀝니다 — 열거 목록을 수동으로 관리할 필요가 없습니다.

## 규칙을 어디에 쓰는가

헤더의 **검증 규칙 행**(기본 5번째 행, 행 역할은 `validation`). 검증이 필요한 열의 5번째 행 셀에 해당 규칙 문자열을 씁니다.

> [!tip]
> 어느 행이 검증 규칙 행인지 모르겠다면? 데모 프로젝트를 가져온 뒤 5번째 행의 색상 표시를 보거나, 열 머리글 우클릭 → CT 속성 → 현재 검증 규칙 보기를 확인하세요.

## 오류는 어떻게 표시되는가

- **실시간 빨강 표시**: 규칙을 위반한 셀은 편집할 때 즉시 빨개집니다, 검증을 돌리길 기다릴 필요 없음
- **호버 툴팁**: 빨간 셀에 마우스를 올리면 어떤 규칙을 위반했는지 툴팁으로 표시
- **검증 로그**: 메뉴 → 검증 로그에서 모든 오류를 나열, **행을 클릭하면 해당 셀로 바로 점프**

## 내보내기 전 차단

내보낼 때(JSON / Protobuf 등) 시스템이 전체 테이블 검증을 다시 한 번 돌립니다. **error가 있으면 내보내기를 차단**(warning은 차단하지 않음):

- 차단(error): `required` / `unique` / `ref` / `enum_ref` 위반
- 통과시키되 경고 표시(warning): `range` / `len` / `regex` 위반

> [!tip]
> 모든 규칙을 error로 처리하고 싶다면? 설정 → 데이터 검증 → 「관대 모드」를 끄세요.

## 파서 특성

- **괄호 인식**: `regex(\(a\|b\))`는 바깥의 `&&`에 의해 잘못 분리되지 않음
- **공백 허용**: `required  &&  range( 0 , 100 )`는 `required&&range(0,100)`과 동일
- **대소문자 구분**: 규칙명은 소문자, 파라미터는 그대로 보존

## 주의 사항

> [!warning]
> `ref` / `enum_ref`는 참조하는 테이블이 이미 프로젝트에 열려 있어야 합니다. 참조 대상 테이블이 프로젝트 내에 없다면 **외부 참조 소스**를 통해 연결해야 합니다([[외부 참조 소스]] 참고).

> [!note]
> 예전 튜토리얼 "데이터 검증"에서 설명한 그래픽 인터페이스 규칙 설정은 v0.0.1 시절의 옛 방식이며, v0.0.2부터 DSL 문자열로 통일되었습니다. 옛 설정은 업그레이드 시 자동으로 DSL로 변환되니 수동으로 바꿀 필요가 없습니다.
